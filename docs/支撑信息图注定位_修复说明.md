# 支撑信息（SI）修复 —— 独立交接文档

> **这份文档只管「SI 插图浮窗」在 Word 版 SI 上的两类问题**：
> **① 图注定位不到**（第 0–7 节，主问题）
> **② 真 Word 表格显示不出来**（第 8 节）
> 每节都给出：症状、根因、完整改法、怎么独立复现、怎么验证。不涉及插件的其它功能。

---

## 0. 一句话根因

SI 文档里的图注写成 **`Fig. S3.`**（缩写 + 句点），而代码拿规范化后的
**`Figure S3`** 当字面量去匹配 —— 于是**整篇 Figure 全部定位不到**。

> 差别只有「`Fig.`」和「`Figure`」+ 一个句点，但结果是"功能整体失效"。

---

## 1. 症状：怎么发现的

用户那篇论文（SI 是 `.docx`）打开后，浮窗**不出图**。查日志
（`<Zotero 数据目录>/zpt-debug.log`，`[si]` 前缀的那些行）：

```
[si] 解析 Word SI 1367: 14926720 字节 → 113 段 / 19 张图（62 ms）
[si] Figure S3 → Word SI 没定位到
[si] Figure S5 → Word SI 没定位到
[si] Figure S6 → Word SI 没定位到
[si] Figure S7 → Word SI 没定位到
[si] Figure S8 → Word SI 没定位到
[si] Figure S17 → Word SI 没定位到
[si] Table S1 → Word SI 只有图注、没有图      ← 这一条**成功了**
```

### ⭐ 关键线索

- **文档解析是好的**：113 段 / 19 张图都读出来了 → 不是解压/解析的问题
- **`Table S1` 能中**，`Figure S3/S5/S6/S7/S8/S17` 全不中

**同样是图注，为什么 Table 行、Figure 不行？** 顺着这个差别查下去就定位到了。

## 2. 根因（带证据）

### 2.1 代码里两条岔路

插件的 SI 图注定位有**两条独立的路**：

| SI 类型 | 定位函数 | 位置 |
|---|---|---|
| PDF | `findCaptionPage` | `src/utils/siRefs.ts` |
| Word（`.docx`） | `findDocxFigure` | `src/utils/docx.ts` |

**PDF 那条路一直是对的**，因为它的类别词用的是**正则变体表**：

```ts
const KIND_WORDS: Record<string, string> = {
  Figure: "Figures?|Figs?\\.?|图",     // ← 注意 Figs?\.?，能吃 "Fig." 和 "Fig"
  Table:  "Tables?|Tabs?\\.?|表",
  Scheme: "Schemes?|方案",
  Chart:  "Charts?|图",
  Equation: "Equations?|Eqs?\\.?|式",
};
```

**Word 那条路漏了这套变体** —— 它把引用标签**当字面量**匹配：

```ts
// 修复前（src/utils/docx.ts）
const reExact = new RegExp(`^\\s*${loose(label)}(?![0-9A-Za-z])`, "i");
//                                     ^^^^^ label 是 "Figure S3"
```

而 `label` 来自 `parseSiRefs()`，它**已经把正文里的引用规范化了**
（`Fig.` → `Figure`，见 `KIND_CANON`）。

所以：**规范化后的 `Figure S3` 去撞文档里的 `Fig. S3.` → 撞不上。**

### 2.2 为什么 Table 能中

那个 SI 里 Table 写的是全称：`Table S1. The elemental content ratios...`
→ 规范化后还是 `Table S1` → 字面量匹配成功。

**一个用缩写、一个用全称，所以一个中一个不中。**

### 2.3 独立复现（不用装插件、不用跑 Zotero）

下面这段 Python 复刻了「修复前」的匹配方式，跑一下就能看到结论：

```python
import re
# 修复前：把标签当字面量（只允许内部空白）
def old_re(label):
    esc = re.sub(r'([.*+?^${}()|\[\]\\])', r'\\\1', label)
    return re.compile(r'^\s*' + esc.replace(' ', r'\s*') + r'(?![0-9A-Za-z])', re.I)

for text, label in [
    ("Fig. S3. XRD image of the ZnSe/NC.",      "Figure S3"),
    ("Figure S3. XRD image of the ZnSe/NC.",    "Figure S3"),
    ("Fig. S6. (a,b) SEM image.",               "Figure S6"),
    ("Table S1. Elemental content ratios.",     "Table S1"),
]:
    hit = bool(old_re(label).match(text))
    print(("✅ 能中  " if hit else "❌ 不中  ") + f"[{label}]  {text[:40]!r}")
```

预期输出（就是线上表现）：

```
❌ 不中  [Figure S3]  'Fig. S3. XRD image of the ZnSe/NC.'
✅ 能中  [Figure S3]  'Figure S3. XRD image of the ZnSe/NC.'
❌ 不中  [Figure S6]  'Fig. S6. (a,b) SEM image.'
✅ 能中  [Table S1]   'Table S1. Elemental content ratios.'
```

> 想看得更细：把 `.docx` 当 zip 打开，读 `word/document.xml`，
> 按 `<w:p` 切段、把每段 `<w:t>` 拼起来，就能看到图注的真实写法。
> 那个 SI 的段落长这样：`Fig. S1. (a-d) SEM image of the ZIF-8 ...`、`Fig. S3. XRD image of the ZnSe/NC.`

## 3. 修复

### 3.1 改 `src/utils/docx.ts`：新增两个函数

```ts
/** 从 `Figure S6b` 里抠出 S 后面的编号与子图字母 */
function splitSiLabel(label: string): { num: string; sub: string } | null {
  const m = /S\s*(\d{1,3})([a-z]?)\s*$/i.exec((label ?? "").trim());
  return m ? { num: m[1], sub: m[2] || "" } : null;
}

/**
 * 生成"段首是这个图注标签"的正则。
 * 必须接受**类别词的缩写写法**（`Fig.` / `Fig` / `Figure`），
 * 否则 SI 图注写 `Fig. S3.` 时整篇 Figure 都定位不到。
 * `kindPattern` 由调用方从 KIND_WORDS 传进来，让 Word 与 PDF 两条路共用同一套写法。
 */
function captionRe(
  label: string,
  kindPattern: string | undefined,
  tail: string,
): RegExp {
  const esc = (s: string): string => s.replace(/[.*+?^${}()|[\]\\]/g, "\\$&");
  const parts = splitSiLabel(label);
  if (!parts) {
    // 解析不出来：老实按字面量找（段首锚定，允许内部空白）
    return new RegExp(`^\\s*${esc(label).replace(/\\?\s+/g, "\\s*")}${tail}`, "i");
  }
  // 类别词：优先用调用方给的变体，兜底给一套常见缩写
  const kind = `(?:${kindPattern || "Figures?|Figs?\\.?"})`;
  // 「S」前后允许空格，类别词后面允许一个句点：Fig. S3 / Fig S 3 / Figure S3 都吃
  return new RegExp(
    `^[ \\t]*${kind}[ \\t]*\\.?[ \\t]*S[ \\t]*${parts.num}${parts.sub}${tail}`,
    "i",
  );
}
```

## 5. ⚠️ 同一个函数里的另一个已修问题（别改回去）

`findDocxFigure` 在**找到图注段之后**还要"就近取图"：

```
优先顺序： 上一段 → 下一段 → 本段 → 上二 → 下二
```

**但距离 2 是有条件的**：只有当中间那一段**不是图注**时才允许。

为什么：真实排版里"图注与图之间夹一个空段"很常见（实测 26 张图里有 2 张这样，
中间段文字为空），所以 ±2 必须留着；但**不加限制的话，一个本身没有图的图注
会隔着邻居的图注把它的图抢过来 —— 面板会显示错误的图**。

```ts
const order: number[] = [hit - 1, hit + 1, hit];
if (!isCaptionParagraph(mids[hit - 1]?.text ?? "")) order.push(hit - 2);
if (!isCaptionParagraph(mids[hit + 1]?.text ?? "")) order.push(hit + 2);
```

**判据**：`isCaptionParagraph()` —— 段首就是 `Figure S1` / `Fig. S3` / `Table S1` 这种标签。
（它的正则本来就含 `Figs?\.?`，所以不需要跟着改。）

## 6. 易错点清单

| # | 坑 | 说明 |
|---|---|---|
| 1 | 只按规范写法匹配文档 | **本 bug 本体**。引用侧会规范化（`Fig.`→`Figure`），文档侧不会，两边必须都容错 |
| 2 | 只修 Word 不修 PDF（或反之） | 两条路是**独立实现**。这次只有 Word 漏了，但改的时候要两边都看一眼 |
| 3 | 忘了 `(?![0-9])` 边界 | 没它 `S3` 会命中 `S30` —— 张冠李戴 |

## 8. 补充修复：Word 里的**真表格**显示不出来

### 8.1 症状

浮窗里出现：

```
Table S2   Word SI 里没有对应图片
Table S2. Etching reaction between carbon and NaOH.
表 S2 碳与 NaOH 之间刻蚀反应
```

图注有了、译文也有了，**但表格本身没有**。

### 8.2 根因

`.docx` 里的表格是 `<w:tbl>` —— **它里面没有 `word/media` 图片**。
而原来的实现只做一件事：**在段落附近找嵌入图片**。表格不是图片，所以永远"没图可给"。

> 对照：**PDF 版 SI 没有这个问题** —— 那条路对矢量内容有"整页渲染"兜底，
> 表格会跟着页面一起出图。**又是只有 Word 这条路缺东西**（和第 2 节那个 bug 同一类）。

顺带一个隐藏问题：原来的解析是 `docXml.split(/<w:p/)`（按段落切），
**表格单元格里的 `<w:p>` 会被顺带切成很多散段落** —— 既把段落序号搅乱，
又可能让某个单元格文字冒充图注。

### 8.3 改法

**① `src/utils/docx.ts`：改成"块模型"解析**（段落 / 表格按文档顺序）

```ts
const BLOCK_RE =
  /<w:tbl>[\s\S]*?<\/w:tbl>|<w:p(?:\s[^>]*)?>[\s\S]*?(?=<w:tbl>|<w:p(?:\s[^>]*)?>|<\/w:body>)/g;
let bm: RegExpExecArray | null;
while ((bm = BLOCK_RE.exec(docXml))) {
  const chunk = bm[0];
  if (chunk.startsWith("<w:tbl>")) {
    const rows = parseTableRows(chunk);
    if (!rows.length) continue;
    paragraphs.push({ text: /* 所有单元格拼起来 */ "", images: [], table: rows });
  } else {
    const para = parseParagraph(chunk);
    paragraphs.push({ text: para.text, images: /* … */ [] });
  }
}
```

`DocxParagraph` 加一个字段：

```ts
/** 本"段"其实是一个真 Word 表格时，这里是它的行列内容 */
table?: string[][];
```

**② 表格 → 行列**（`parseTableRows`）：

```ts
function parseTableRows(xml: string): string[][] {
  const rows: string[][] = [];
  for (const tr of xml.match(/<w:tr[\s>][\s\S]*?<\/w:tr>/g) ?? []) {
    const cells: string[] = [];
    for (const tc of tr.match(/<w:tc(?:\s[^>]*)?>[\s\S]*?<\/w:tc>/g) ?? []) {
      // ⚠️ 单元格里常有**多个段落**（化学方程式就是一个反应一行）。
      //    直接把所有 <w:t> 拼成一串会粘成 "2H22NaOH"，必须按段落切、段间补换行。
      const paras = tc.match(/<w:p(?:\s[^>]*)?>[\s\S]*?(?=<w:p(?:\s[^>]*)?>|<\/w:tc>)/g) ?? [];
      const lines = paras.map(/* 取该段的 <w:t> 拼接 */).filter(Boolean);
      cells.push(lines.join("\n"));
    }
    if (cells.length) rows.push(cells);
  }
  return rows;
}
```

**③ 找表格的规则**（和"取图"不一样，见下）：

```ts
function findNearbyTable(paras, hit) {
  // 先往后找，遇到下一个图注段就停；再往前找，同样遇到图注就停
  for (let i = hit + 1; i < paras.length; i++) {
    if (isCaptionParagraph(paras[i].text)) break;
    if (paras[i].table?.length) return paras[i].table;
  }
  for (let i = hit - 1; i >= 0; i--) {
    if (isCaptionParagraph(paras[i].text)) break;
    if (paras[i].table?.length) return paras[i].table;
  }
  return null;
}
```

> ⚠️ **为什么不能照搬取图的"±2 就近（上一段优先）"**：
> 实测某 SI 的块序列是
> `[10] Table S1 图注 → [11] Table S1 表格 → [12] Table S2 图注 → [13] Table S2 表格`
> 若"上一块优先"，**Table S2 会抢走 Table S1 的表**。
> 表格是**块级**的，必须"遇到下一个图注就停"。

**④ `src/utils/siRefs.ts`**：`SiTarget` 加 `table: string[][] | null`，Word 分支带上它
（PDF 分支给 `null`），日志加一档 `配到表 N×M`。

**⑤ `src/modules/siBox.ts`**：渲染成 HTML `<table>`
（`border-collapse: collapse`、首行加粗当表头、`white-space: pre-wrap` 保留单元格内换行）。
**全部用 `textContent` 赋值** —— 单元格文字是从文档里抽的任意字符串，拼 `innerHTML` 等于自己开注入口子。

### 8.5 ⭐ 上下标必须还原成 LaTeX（否则化学式是错的）

**这一步不能省。** 上面把表格取出来后，显示的是 `Na2CO3` —— **化学式是错的**。

查 `.docx` 才发现：那个 `2` 是**独立 run**，带下标标记：

```xml
<w:r><w:rPr><w:vertAlign w:val="subscript"/></w:rPr><w:t>2</w:t></w:r>
```

只把所有 `<w:t>` 拼起来，格式就丢了。

**改法**：单元格取字改成**按 run 走**，遇到 `vertAlign` 就转成 LaTeX 行内公式：

```ts
function paragraphTextWithScripts(pp: string): string {
  let out = "";
  for (const run of pp.match(/<w:r(?:\s[^>]*)?>[\s\S]*?<\/w:r>/g) ?? []) {
    const txt = /* 取该 run 的 <w:t> 并反转义 */;
    if (!txt) continue;
    const va = /<w:vertAlign\s+w:val="(subscript|superscript)"\s*\/>/.exec(run);
    if (va) {
      const mark = va[1] === "subscript" ? "_" : "^";
      // ⚠️ 空格要留在公式**外面**：`'3 '` 这种 run 的尾随空格是词间分隔，
      //    塞进 `$_{3 }$` 会变成"下标里带空格"；直接 trim 又会把 `Na2CO3 + 2C` 粘成 `Na2CO3+ 2C`
      const lead = /^\s*/.exec(txt)![0];
      const trail = /\s*$/.exec(txt)![0];
      const core = txt.trim();
      out += core ? `${lead}$${mark}{${escMath(core)}}$${trail}` : txt;
    } else {
      out += txt;
    }
  }
  return out.replace(/[ \t]+/g, " ").trim();
}
```

`escMath()` 把 `\ { } $ % # & _ ^ ~` 转义（下标内容一般只有数字字母，但别赌）。

结果：`Na$_{2}$CO$_{3}$` → 插件用**本来就有的 KaTeX** 渲染成 Na₂CO₃。
实测那份表格渲染出 **15 处 KaTeX 公式**。

> **为什么不"把表格截成图"**（也回答"为啥不截屏"）：
> 1. **插件里没有 Word 渲染器**。PDF 版能出图是因为 pdf.js 能渲染页面；
>    `.docx` 没有等价的渲染器 —— "截屏"不是免费的，要自己写一个 canvas 表格渲染器
>    （算行高、换行、画线、画字），上百行且容易和 Word 的真实排版对不上。
> 2. **文字表其实更好用**：可选中、可复制、跟着浮窗缩放不糊；图是定死的位图。
> 3. 真正让人不满的是"化学式看着不对"，而那**是上下标丢了** —— 用 LaTeX 还原即可，
>    比截图更准，代价也小得多。
>
> 如果确实要图（比如表格很复杂、有合并单元格），再另说 —— 那是另一条路。

### 8.7 ⭐ 拖浮窗会拖动整个窗口（阅读器工具栏是「窗口拖动区」）

**用户反馈**：「支撑信息的框我一拖动，就把整个软件拖动了」。

**根因（在 Zotero 自己的 CSS 里）**：

```css
/* resource/reader/reader.css */
.toolbar{ ... -moz-window-dragging:drag; ... }        /* ← 阅读器工具栏就是窗口拖动区 */
.utility-popup{ ... -moz-window-dragging:no-drag }    /* ← Zotero 自己的浮层特意挖掉 */
```

浮窗被放在 `y=10`，**正好压在那条 41px 高的工具栏上**。
而 Firefox 的窗口拖动区是**窗口级矩形** —— 不管谁盖在上面，只要按下点落在那块区域，
就被当成"拖标题栏"，整个 Zotero 窗口跟着鼠标走。

> ⚠️ 排查时走过一个弯路：查「祖先链上有没有 `-moz-window-dragging: drag`」**查不出来** ——
> 因为浮窗是 `.toolbar` 的**兄弟节点**（都挂在 reader 文档 body 下），不是子节点。
> 必须用**几何重叠**判断：浮窗矩形和 `.toolbar` 矩形有没有相交。

**改法（双保险）**：

1. **浮窗自己挖出拖动区**（照 Zotero 自己的做法）：
   ```ts
   panel.style.setProperty("-moz-window-dragging", "no-drag");
   head.style.setProperty("-moz-window-dragging", "no-drag");   // 标题栏同样
   ```
   > 用 `setProperty` 而不是 `style["-moz-window-dragging"] = ...` ——
   > 它是非标准属性，`setProperty` 更稳。

2. **上边界卡在工具栏下方**：初始化 + 拖动时都把 `y` 限制在 `.toolbar` 底边之下，
   让浮窗**压根不压到那块区域**：
   ```ts
   function topLimit(doc: Document): number {
     const tb = doc.querySelector(".toolbar") as HTMLElement | null;
     if (tb) { const b = tb.getBoundingClientRect(); if (b.height > 0) return Math.ceil(b.bottom) + 2; }
     return 0;
   }
   ```

3. 另外补了 `mousedown` 与 `dragstart` 的拦截（Firefox 的原生窗口拖动是**在 mousedown 上**判定
   的，只在 `pointerdown` 里 `preventDefault` 未必拦得住）。

**取证日志**（浮窗创建时打一行，便于以后复发时确认）：

```
[si] 浮窗文档=外层(reader) | 工具栏拖动区=drag 与工具栏重叠=是 浮窗自身=no-drag
```

### 8.8 已知边界

- **不还原合并单元格**（`gridSpan` / `vMerge` 目前忽略，按原始单元格数排）。
- **单元格里如果是 Word 公式对象（OMML，`<m:t>`）取不到** —— 只认 `<w:t>`。
  （实测那份 SI 的化学方程式都是普通 `<w:t>`，能完整取到。）
- 表格**不翻译**（只显示原文 + 翻译图注）。化学方程式这种本来就不需要翻译；
  若需要译文，可以后续接同一条翻译链路。
